## Step 4 — what changes in our backlog / posture

### NEW: H_SMART_CLUSTER_VETO — production-relevant negative signal

**Filter**: when SNIPER_SMART_CLUSTER fires on a token (regardless of which other streams also fire), the token is a near-certain rug. Walk-forward TRAIN/VAL/TEST = -90.2 / -100 / -100. Rug 92/100/100. WR 4/0/0. 

**Why it's not just stream-dedup-noise**: under the current production dedup (SNIPER_A wins), SMART_CLUSTER rows never become live trades. So as a **veto on already-live entries**, the signal is: "if SNIPER_SMART_CLUSTER is in the multi-stream-fire set for a token, abandon the trade."

**Coverage**: 41 tokens out of 572 = 7.2%. In the last 48h that's 30 tokens out of ~400 = 7.5%. 100% rug in the last-48h TEST window.

**Mechanism (hypothesis)**: SMART_CLUSTER fires on tokens with a "cluster" of smart-money buyers. But the cluster being detectable enough to fire SMART_CLUSTER might actually mean a bundle of correlated wallets sniping the token's launch — i.e., an insider bundle, not smart money. Insider bundles correlate with rug.

**Status**: NEW. Highest-priority deployment candidate this cycle. Implementation cost: ~5 LOC — read each pending trade's multi-stream set, skip if `SNIPER_SMART_CLUSTER ∈ set`.

**Caveat**: the dedup keeps earliest stream; SMART_CLUSTER stream-row data is observable only AFTER the trade fires (SNIPER_A enters first, then SMART_CLUSTER's detection fires later). To use this as an entry-side veto, we need a real-time multi-stream concurrency check on detect-side, not on close-side. The brain doesn't know whether the sniper architecture supports that without reading code.

### NEW LESSON (extends cycle_1200 negative lesson)

The cycle_1200 finding "H_DISTRIB/H_LOCKED/H_QUIET_EMERGENCE are anti-fat-tail rug-reduction filters" generalises:

**STREAM-LEVEL Track A is ALSO anti-fat-tail.** SNIPER_G/GOLD5/WHALE catch 0/3 known bigs. They are stream-level analogs of feature-level rug-reduction filters — same trade-off, same regime artifact, same walk-forward failure.

**Strategic implication**: the path to +1M% is NOT "find the safest stream" or "find the safest filter". Both routes give us small data, anti-fat-tail correlation, and walk-forward instability. The path is "find a fat-tail-capturing filter that we can deploy with Kelly-correct sizing".

**Practical implication for the 2-track question (carrying from cycle_1200)**: TRACK A as currently scoped (stream selection + rug-reduction filter selection) does not produce a deployable edge. Either (a) abandon Track A entirely, or (b) re-scope Track A to mean "Kelly-sized exposure to ALL streams during fat-tail-present regime" (i.e., a sizing rule on the existing system, not a filter sub-selection).
