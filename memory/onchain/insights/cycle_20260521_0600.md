## Step 6 — Why H_V6 and H_BSC_BC_FULL both fail the same way (meta-lesson)

Both shapes:
1. Catch every big in the dataset (4/4 / 6/6).
2. Pass on the TRAIN split that contains the bigs.
3. FAIL on TEST split that doesn't contain the bigs.
4. Have bigs cluster in a single short event window (BSC: 4 hours; SPCXDRAGON+GITBANK: 70 seconds).

**Generalised observation**: in current memecoin regime (May 2026), fat tails arrive as **event-cluster bursts** rather than uniformly. A single 4-hour BSC narrative window or a 70-second Sol pump-event accounts for 5-6 bigs each. Per-token feature-based filters that match those bigs also match the surrounding (failed) tokens that share the same features, because they're all triggered by the same launch-pattern templates that the cluster event amplifies.

**Implication**: feature-based walk-forward will repeatedly produce this shape:
- Bigs in single cluster window → TRAIN passes, TEST fails (or vice-versa).
- Per-token features are NECESSARY but not SUFFICIENT — they're correlated with the cluster events but not with prospective entry timing.

**New hypothesis class**: **cluster-onset detection** — instead of filtering tokens by static features, detect that we're INSIDE a fat-tail cluster window and trade aggressively during it. Candidate signals:
- Rolling-window big%>0 in last N tokens (Bayesian fat-tail-presence indicator).
- Cross-token pattern: when 2+ tokens fire on the same shape within 5 minutes AND one of them pumps >100%, raise sizing on subsequent tokens in same shape.
- Inverse-regime gate (H_REGIME_GATE_INVERSE): **when last-10-window big%>0 and rolling-window avg>-30%, raise position size**.

This is a **regime-aware sizing rule**, not a per-token feature rule. It's a logical extension of H_REGIME_GUARD: the guard says "stop trading in dead regime"; the inverse says "size up in fat-tail-live regime".

**Status**: NEW (proposed), needs cluster-onset definition + walk-forward backtest. Promising direction.
